# Apocalypse：11 種新版 OR-Tools 人機

本倉庫只交付 **11 個可獨立匯入的 bot 與這份 README**。策略依新版遊戲重新設計；不包含學員程式、地圖、遊戲主程式或測試工具。

對應遊戲版本：[Neoxy-6/Apocalypse `f464379`](https://github.com/Neoxy-6/Apocalypse/tree/f4643792dafca59cfe567f82bba1af69f61d1546)，介面沿用原版 `apocalypse_sdk.State`。地圖、分數、難度及勝利條件均由原版遊戲決定。

## 11 種策略

單一求解器 8 種、混合求解器 3 種。名稱是優先偏好；每種都能處理搬運、加工、工程、救援、補給及撤離。

| # | 策略／檔案 | 求解器 | 決策重點 |
|---|---|---|---|
| 1 | [套件架構師](bot_01_set_architect.py) | CP-SAT | 將完整套件視為有條件的整體收益，選擇同趟收齊的組合。 |
| 2 | [期限精算師](bot_02_deadline_accountant.py) | CP-SAT | 同時考量抵達時間、逾期衰減及保底獎勵，優先保住會快速失去的價值。 |
| 3 | [產線統籌師](bot_03_flow_controller.py) | CP-SAT | 加工前後任務的相依排程；先卸貨、等待加工、再取成品。 |
| 4 | [救援配置師](bot_04_rescue_optimizer.py) | CP-SAT | 將民眾搬運、倒地隊友的救援期限與其他工作一起分配。 |
| 5 | [環線集運師](bot_05_milk_run.py) | Routing | 多點取送、背包容量與整趟路程，集中處理能順路完成的工作。 |
| 6 | [加工接力師](bot_06_factory_courier.py) | Routing | 優先安排工廠間取送與後續成品，利用中途卸貨釋放容量。 |
| 7 | [巡邏時窗師](bot_07_safe_window.py) | Routing | 在取送點加入公開的殭屍危險時窗限制，並提高路線風險成本。 |
| 8 | [輕載速運師](bot_08_light_express.py) | Routing | 主動採用 12 重量的規劃上限、較少候選任務及較高時間成本。 |
| 9 | [跨河套件師](bot_09_cross_river.py) | CP-SAT → Routing | 先選完整套件，再重排跨區取送順序；與原 CP-SAT 路線比較後採用。 |
| 10 | [武裝調度師](bot_10_armed_scheduler.py) | CP-SAT → Routing | 將軍火庫補給也列為可選工作，提高武裝收益，再調整任務路線。 |
| 11 | [主線總調度](bot_11_mission_director.py) | CP-SAT → Routing | 提高直升機零件的主線價值，隨主線落後程度調整收益，兼顧加工及燃油。 |

## 使用方式

使用 Python 3.10 以上、對應版本的原版 SDK，安裝：

```bash
python -m pip install ortools==9.15.6755 "requests>=2.28"
```

確保原版 `apocalypse_sdk.py` 和選用的 bot 檔案可被匯入：

```python
from bot_01_set_architect import make_policy

policy = make_policy()       # 每位角色、每場比賽各建一個實例
steps = policy(st)          # st：原版 apocalypse_sdk.State
# steps 是行動串列時，沿原版流程提交，start_node=st.here。
# steps 是 None 時，維持原本的計畫。
```

同一場持續使用同一個實例，每秒呼叫一次，移動中也要呼叫，讓治療、失效任務和撤離判斷能即時執行。檔案本身不連線、不註冊角色、不啟動遊戲，連接方式沿用原版 notebook。

每次單一求解器預設搜尋 **0.3 秒**；混合策略最多各搜尋 0.3 秒，另有建模時間。可透過 `policy.solve_seconds` 調整。普通計畫遵守新版 **30 秒**冷卻，實際以 `st.you['next_plan_at']` 為準；緊急治療、丟棄及撤離沿用原版例外。正在執行的有效計畫會持續完成，不會每秒重解。

## OR-Tools 實際負責的工作

- **CP-SAT**：可選工作、取送先後、逐點載重、載重造成的速度變化、加工延遲、交付時間、整套完成獎勵與行程時間。同趟只在末段回撤離點，避免把不同趟交付誤算為同趟套件。
- **Routing**：可選取送配對、時間與載重維度、加工相依、危險時窗及有條件獎勵節點。逾期收益有下限，完整套件才有額外獎勵；已背在身上的有效貨物必須安排交付。
- **混合策略**：CP-SAT 先決定工作集合，再讓 Routing 改善順序，並比較實際路線評估值。兩者都真的呼叫求解器。

候選任務會先篩選，避免把整張地圖所有任務塞入短時間模型。圖上搜尋用於距離與合法道路展開；緊急處理使用直接規則。一般工作的選擇及排程經過 OR-Tools，沒有以貪心計畫冒充求解結果。暖啟動只是交給求解器的初始可行方案。

共用的預設規劃視野最多 125 秒。Routing 的模型採估計載重速度，CP-SAT 則隨載重變化；輸出時兩者都重新按當前載重展開路徑、插入預告／加工等待並檢查容量及期限。取藥、取武器也會占重量。公開隊友意圖會降低重複搶單的吸引力。

## 測試結果

**78 項檢查通過**，直接匯入本倉庫的 11 個獨立檔案測試，涵蓋完整套件、加工前後相依、卸貨釋放容量、逾期保底、預告等待、已攜貨物返程、冷卻，以及危險時窗。

另有容量取捨案例：附近單件值 150 分，但會擠掉總值 620 分的三件完整套件。以單件距離／分數選擇的貪心會先拿 150 分單件，11 個 bot 都選出完整套件。這是組合規劃的具體例子，不能解讀為任何局面都勝過貪心。

完整對局使用原版模擬器、原版地圖生成及預設規則，12 人組合為「11 個新版 bot ＋ 1 個原版貪心範例」。對照組是 12 個原版貪心；同種子、同時間步長，提交包含求解耗時與額外 0.15 秒延遲。結果如下：

| 種子／時間步長 | 新版組合：撤離人數／零件 | 貪心對照：撤離人數／零件 |
|---|---|---|
| 42／0.05 秒 | 10/12 人，112/112 | 0/12 人，69/112 |
| 7／0.1 秒 | 7/12 人，113/112 | 12/12 人，116/112 |
| 99／0.1 秒 | 12/12 人，116/112 | 12/12 人，116/112 |

測試數量有限，求解時間受電腦負載影響，不能視為勝率保證。不同策略共用生存與撤離處理，戰績差異不只來自求解器。殭屍追逐、任務被其他人取走、封路與移動誤差都會讓預測失準；公開危險時窗只涵蓋未來一段時間，不能保證全程無傷。求解採時間限制與候選篩選，未宣稱全域最優。

另已在原版 Unity Windows 建置中，以原 repo 的設定檔、種子 42、正常 1 倍速，跑完「11 個交付 bot ＋ 原版 starter_bot 學員範例」完整一局：**12/12 人撤離、零件 112/112、燃油 6/6**。11 個 bot 皆有實際求解與提交計畫；無 API／提交錯誤。此為 Unity 實測，與上表 Python 模擬器結果分開記錄。
